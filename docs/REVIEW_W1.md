# Week 1 review — agent correctness and the Milestone 2 release gate

**Decision:** Do not ship cross-device access until authorization covers `/chat`'s indirect actions as well as the dedicated routes. Do not add more effectful tools until approval is bound to one dispatch and cancellation has an honest, durable outcome. The identity/conversation work can proceed independently if effectful capabilities that cannot meet those guarantees stay disabled or out of reach.

**Evidence:** Reviewed the supplied archive, starting with `docs/PROJECT_PLAN.md` §1 and `docs/AUDIT.md`. “M2” below means identity + durable conversations from the current plan; the older audit also calls the existing agent engine “Milestone 2.” Ran `python -m pytest -q -rs -p no:cacheprovider` in an isolated environment with FastAPI installed: **128 passed, zero skips**. The first run without FastAPI reported 92 passes and three collection skips; CI must reject that false green. Findings below are code-path analyses against those tests, not claims that new race tests or mutations have been run. No live model, Android, Windows or M2 implementation was verified. Paths below are relative to the archive root; `agent/` and `llm/` refer to `backend/core/`.

## 1. Findings, in priority order

| Rank | Input or event → wrong behavior | Why the baseline tests miss it / regression oracle |
|---|---|---|
| **1 · High — `/chat` is a second authorization path** | A normal chat request is classified as an app/site action or a memory mutation → `backend/api.py:90–145` calls legacy tools or memory directly, without the agent policy in `agent/engine.py:129–142`. A deny in the agent policy therefore does not govern the same action through chat. M2 makes this a release blocker if a chat-only device can exercise the indirect capability. This already affects built-ins; it does not require a future level-3 tool. | `test_tool_intent_uses_local_classifier_and_runs_tool` checks legacy execution and `test_memory_save_then_recall_roundtrip` treats the indirect write as success; `test_policy_endpoints_validate_persist_and_block` checks `/agent` only. Assert both entry points honor the same action policy and device permission, with no handler call or state change on denial. |
| **2 · High — approval is a mutable task flag, not a one-use decision** | Two decisions arrive for a single pending step before the worker consumes the event → both can be acknowledged and the later write can replace the first. A delayed response cannot be distinguished from a response to a newer step: `agent/routes.py:22–23,63–69` carries no step/window identity. An approval arriving after the nominal deadline but before the next timeout poll can still win (`manager.py:55–72,126–143`). Cancellation recorded before dispatch can likewise lose to the `answered` path: it returns `approved`, and `_execute` submits before its first cancellation check (`engine.py:139–173`). A deny policy committed while approval is pending is also not rechecked at dispatch. No shipped level-3 tool; configurable level-2 confirmation already uses this path. | `test_manager_confirmation_approve_and_deny`, `test_cancel_while_waiting_for_confirmation`, `test_manager_confirmation_timeout_counts_as_no` and the HTTP equivalents exercise isolated outcomes, not collisions. Barrier-test duplicate/conflicting decisions, stale window, either side of expiry, cancel before dispatch, and policy change while paused. Exactly one decision wins; no stale approval or pre-dispatch cancellation yields a handler call. |
| **3 · High — cancellation/timeout abandons the observer, not the action** | A handler is still running when the caller gives up → `Future.cancel()` cannot stop that thread (`agent/engine.py:159–173`). A tool timeout is an ordinary `ToolError`, so the replan can dispatch another copy while the first still runs. Cancelled/task-timed-out steps raise before `on_steps` and `audit`, leaving no record of the in-flight action; separate commits for steps and audit create another crash window (`engine.py:105–110`; `store.py:45–58,88–96`). A restart marks the task failed, not the effect undone. Four blocked handlers can occupy the entire default tool pool. | `test_tool_timeout_is_reported` and `test_cancel_interrupts_a_running_tool_promptly` assert caller latency and explicitly release their harmless blocked handlers. `test_audit_hook_called_per_step` never interrupts an action; `test_restart_recovery_marks_inflight_tasks` inserts a task row without an action. Hold a fake handler, observe its actual invocation count and durable state, and prove no automatic retry of an unknown effect. Before effectful operators ship, require a killable/cooperative runner or an explicit unknown-outcome state with reconciliation and an idempotency strategy; killing a runner does not undo an already committed effect. |
| **4 · High — persisted policy can silently loosen** | A present but incomplete legacy policy record loads → missing `deny` becomes empty and missing `max_auto_level` becomes 2. A string where `deny` should be a list becomes a set of characters, so a previously intended tool deny no longer matches (`agent/__init__.py:34–38`; `policy.py:19–25`; `store.py:109–117`). A syntactically invalid JSON row is different: it fails load, not silently. Additionally, the policy route changes live state before SQLite commits; a failed write can leave enforcement different from what the caller and a restart see (`routes.py:88–96`). A level-only write also clears denies by default unless the caller supplies them. | `test_store_tasks_actions_settings_and_recovery` only round-trips a partial dict, never builds with it; `test_policy_endpoints_validate_persist_and_block` checks a live update, not restart or write failure. Test full restrictive round-trip, explicitly supported migration, malformed typed records and injected commit failure. Publish an immutable, durable revision as a unit; reject or fail closed on unsupported stored state. Document full replacement vs patch semantics. |
| **5 · High if `local_only` is a privacy boundary — mutable routing preference doubles as a lock** | A previously local-only task route is replaced by a saved or API route that lacks `local_only` → it defaults to false; routing can then send a request that has no independent `allow_cloud=False` constraint to a cloud provider (`llm/config.py:61–63,79–88,145–170`; `llm/routes.py:40–42,76–84`; `router.py:79–105`). This does **not** remove `/chat`'s existing explicit personal-memory opt-in check. It matters for any caller relying on the route flag alone, including future history-aware paths. | `test_local_only_task_never_goes_to_cloud_even_when_selection_is_gemini` and `test_allow_cloud_false_forces_local` start with the expected policy intact; `test_local_only_route_rejects_cloud_target` tests the true-flag case only. With fake providers, assert zero cloud calls after a preference update/reload when data is classified local-only. Keep mandatory data residency separate from route preferences. |
| **6 · Medium — schema-valid is not goal-valid** | “Calculate 25 × 35” produces a valid `calculate` step with `25+35`, or “Open YouTube” yields an empty/omitted `steps` → engine can return a verified but wrong computation or send an action request through answer mode (`agent/planner.py:17–35,77–89`; `engine.py:93–98,132–148`; `builtin.py:68–70`). A known tool with schema-valid arguments can still act on the wrong target. | `test_multi_step_success_is_verified_and_reports_only_tool_output` stipulates correct scripted arguments; `test_eval_planner_scores_valid_and_correct` and `scripts/eval_planner.py:27–40` compare names/order only. Score expected arguments, negative constraints and complete goal coverage; distinguish answer, unsupported goal and action. Require validation or explicit confirmation of the actual target for meaningful effects, not just model confidence. |
| **7 · Medium — bounded replanning still permits repetition and false success** | A failed step produces the same normalized plan, or a replacement repeats an earlier successful step → the engine runs it again; a replacement with no steps exits the loop and returns `succeeded` even though the goal remains unresolved. The old queue is replaced wholesale and the persisted plan remains the original one (`agent/engine.py:102–126`; `planner.py:67–74`). This is bounded by default, not an infinite loop. | `test_failure_after_replan_budget_fails_with_clear_error` actually expects two identical failing attempts. `test_failed_verification_fails_the_step` scripts an empty replacement and only checks the step, not the final status. Assert empty recovery is not success, completed effectful steps are not replayed, residual goal coverage is demonstrated, and retries are limited to explicitly retry-safe failures. |
| **8 · Medium — the clock is paused, but execution boundaries do not enforce it** | A human's valid wait should restore only the active budget left on entering confirmation. Current code credits publication and the worker's wake-up delay as part of the pause and admits approval without checking the confirmation deadline (`agent/manager.py:55–72`). Approval can then lead to immediate submit even if cancellation/deadline is already decisive. A fast future can return before `ctx.check`, and a slow answerer/verifier or replan can finish after timeout or cancellation without a check before final success (`engine.py:93–126,142–173`; `manager.py:98–113`). Two waiting approvals also tie up both default task workers; queued time is outside the task budget. | `test_whole_task_timeout` covers a slow tool that keeps polling, not answer/verification/replan or the fast-result race. No existing test advances a clock across a human wait and measures the remainder. With a fake monotonic clock, prove a timely human wait preserves exactly the remaining active budget, expiry at the boundary rejects, blocked answer/verification cannot publish late success, and the queued-time contract is explicit. |
| **9 · Medium — retry accounting is accurate after the call, too late to enforce limits** | With a one-request limit, the first provider attempt records a retryable failure → `llm/router.py:132–162` retries without a fresh budget check; parallel requests can both pass the last-slot check before either records. An implicit model target and the same explicit default name are deduped before resolution (`router.py:107–112,126`), so a single logical request can get two retry batches when no cooldown/budget stops the second. | `test_local_budget_blocks_cloud_and_falls_back` uses successive successful requests; `test_usage_is_recorded_per_attempt_including_failures` sets no limit. Assert atomic pre-dispatch reservation per resolved provider/model, including retries; skipped targets add no network row; fallback usage is attributed to its actual provider, and an aliased target is not attempted twice. |
| **10 · Medium — cooldowns follow the last error and can move backwards** | A long cooldown recorded by one request can be overwritten by a shorter cooldown from another request already in flight (`llm/router.py:160–194`; `usage.py:114–127`). Auth cooldown is model-keyed even though the Gemini credential is shared, so a fallback to a different model with the same bad credential is still tried. Cooldowns also disappear on process restart, unlike usage; specify whether that reset is intentional. | `test_persistent_429_falls_back_to_ollama_and_sets_cooldown`, `test_auth_error_cools_down_gemini_for_minutes_not_forever`, and `test_budget_and_cooldown_expiry` use sequential calls and one model. Barrier-test competing cooldown writes; an existing longer hold survives, auth failure suppresses siblings sharing the credential, and unrelated providers still work. Keep genuinely model-scoped quota separate. |
| **11 · Medium — retry wait budget is not a request deadline** | Slow provider attempts followed by fallback → `llm/retry.py:47–69` counts only sleep per target, resetting at each fallback; network time is outside the budget and provider timeouts are configured independently (`llm/config.py:108–112`). `max_delay` is capped before jitter, so it is not even a hard cap on unhinted sleep; honoring server `Retry-After` as a floor is a separate, intentional exception. | `test_gives_up_when_wait_exceeds_budget_so_router_can_fall_back` and `test_jitter_stays_in_bounds` exercise synthetic sleeps, not network wall time plus two targets. Pass one absolute deadline through attempts/backoff/fallback, and test that exhausted time prevents further network work. |
| **12 · Medium — saved settings reload is not all or nothing; fallback flag is ambiguous** | A saved file with a valid selection and early route plus a later invalid route → `llm/config.py:157–170` silently retains already-applied changes; some wrong shapes instead raise uncaught `TypeError`/`AttributeError`. Runtime settings mutate before `_persist` (`router.py:48–73`), so a failed save can leave live and restart views different. In `auto`, an explicitly configured local target remains when `fallback_to_local=false` (`router.py:88–105`); define whether the flag disables only the extra safety net or all local fallback and make the API say which. | Config tests cover valid precedence, clean round-trips and wholly malformed JSON, not partial application/persist failure. `test_fallback_disabled_raises_when_cloud_fails` tests explicit Gemini selection, not `auto`. Test atomic rejection of partially invalid configs and the agreed behavior for explicit targets. |

**Biggest architectural mistake:** Authorization and execution state live in wrappers, not at the action boundary. `/chat` can take a different path to an effect, while plan, approval, dispatch, cancellation and audit are separate operations with independent sources of truth. Keep the planners and providers; put every action through one policy-checked dispatch contract with a durable attempt ID and explicit state transitions. A confirmation authorizes one normalized action, not a task ID or an arbitrary future step. Record dispatch intent before execution; recover an interrupted attempt as unknown until reconciled, not as evidence that nothing happened.

## 2. M2: acceptance gate and mutation checklist

**Set the contract before testing.** A and B are separate device identities with access to the same owner/workspace; C is outside the conversation's authorization boundary. If M2 is single-owner, use an explicit inaccessible fixture or a separate workspace where supported; at minimum prove revoked/unenrolled devices and devices without read scope get nothing. A conversation ID is a selector, not a credential. Enrollment must use server-issued grants; clients cannot choose their own privileges. Only explicitly public routes (health and the strictly limited redemption endpoint, plus any intentional landing route) bypass device auth. Protect device bearer transport with verified TLS or an authenticated tunnel for cross-device use; keep the baseline cleartext Android configuration out of release. Never send tokens in URLs.

**Recommended chat contract:** Persist a complete user/assistant turn atomically before returning success; allocate an immutable server sequence scoped to the conversation at commit, with user then assistant adjacent, and paginate by that sequence, not device time. Competing calls may commit in completion order; both readers must agree on the order. Each answer uses a committed history snapshot; this by itself does not promise that overlapping requests see each other's prompts. A later request must see prior acknowledged turns. If product instead promises acceptance order or causally ordered replies, serialize/reserve turns accordingly and invert the completion-order fixture; don't silently infer either guarantee. Use a client request ID scoped to the authorized caller and conversation if automatic retries are enabled. Model execution stays outside the DB write transaction; recheck identity/scopes at commit for a write that spans model execution.

Each mutation is a conceptual one-line weakening for the future implementation, not production code. Apply it alone in an isolated checkout against fake providers and seeded test identities. Require the named test to go red on its **behavioral assertion**, not because the mutant does not compile or a fixture cannot start. Revert and require green. A bundled fixture can cover one guarantee in multiple variants; kill each corresponding mutant independently.

| ID / test | Pass criterion | One-line mutation that must fail |
|---|---|---|
| **E1 · Pairing issuance** | Non-admin and anonymous requests cannot issue pairing grants; the documented trusted bootstrap/admin flow can. | Remove the issuer privilege check. |
| **E2 · Invalid/expired pairing** | Unknown, malformed and expired grants (including exactly at expiry) mint no device/token; a valid grant still works. | Treat expiry equality as valid. |
| **E3 · One-time redemption** | Two concurrent attempts against one grant yield exactly one enrolled device and one usable token; all later attempts fail. | Skip consuming the grant in the redemption transaction. |
| **E4 · Enrollment privilege binding** | Trying to override the grant's owner, device identity or allowed scopes cannot change the issued identity or widen its scopes. | Derive granted scopes from the enrollment request instead of the grant. |
| **E5 · Enrollment abuse budget** | Invalid attempts hit the configured redemption limit even with varied codes; a legitimate attempt from an independent bucket still works; the blocked call mints nothing. | Key the limiter on the submitted code instead of the trusted requester bucket. |
| **E6 · Failed redemption rollback** | Fail device/token insertion mid-redemption: no partial record or credential escapes, and the still-valid grant can subsequently redeem once. | Commit grant consumption before device creation. |
| **T1 · Token issuance and storage** | Two enrollments produce distinct high-entropy opaque tokens; bearer verification works, but raw tokens do not appear in persisted state, logs or list/error responses; issuance uses the OS-backed random generator. | Persist the bearer itself instead of its verifier. |
| **T2 · Rotation and restart** | After rotation commits, old token is immediately rejected and new token works both before and after restart, with the same device ID/scopes and no effect on other devices. | Leave the previous verifier active when rotating. |
| **T3 · Rotation atomicity** | Inject a failed rotation: the old token remains valid and no replacement is exposed; concurrent successful rotation obeys one documented winner rule with exactly one active token. | Invalidate the previous verifier in a separate transaction before issuing the replacement. |
| **T4 · Immediate revocation** | Warm authentication with a valid token on two app instances; once revocation commits, the next request on either instance fails without a grace window, including across restart; B stays authorized. | Trust the prior positive auth result until a cache TTL expires. |
| **T5 · In-flight write revocation** | Pause A's authenticated chat after request entry, revoke A, release the fake model: no success or durable chat turn after revocation wins the commit race. Already-dispatched work is not represented as undone. | Remove the final authorization check from the commit boundary. |
| **S1 · Authentication vs authorization** | Missing/malformed/unknown tokens receive 401 on protected routes; valid tokens lacking the relevant scope receive 403; denials perform no downstream call or write. | Treat absence of credentials as a default authenticated device. |
| **S2 · Protected route inventory and indirect effects** | A read-only token cannot chat-write; a chat-write-only token cannot list history or trigger memory mutations, device/admin operations or protected agent actions via another path; assert zero downstream effect for every denied route/intent. | Replace the indirect action's capability check with the generic chat-write check. |
| **S3 · Object-level authorization** | A credential with the right general scope but no grant to a seeded conversation cannot read, list or append it; use a non-disclosing response if existence is sensitive. | Look up the conversation by ID alone instead of applying the access predicate. |
| **S4 · Server-owned attribution** | Submitting another device ID, a forged role or a client sequence cannot change stored authorship, role or sort order. | Store the body-supplied device ID instead of the authenticated device ID. |
| **S5 · Release transport** | A release client connects through verified encrypted transport and refuses an insecure bearer destination; no plaintext-token fallback on connection failure. | Allow cleartext traffic for the release client. |
| **C1 · Shared persistence and context** | A writes; B reads the same conversation ID, canonical message IDs, content, roles and A attribution, then B writes and A sees it; inspect the fake provider input to confirm B's later reply saw A's committed turn and not another conversation. | Partition conversation history lookup by device ID instead of the authorized conversation. |
| **C2 · Explicit conversation selection** | Omitted or empty conversation ID follows a documented rule (reject or create a new authorized conversation) and never reads/writes a global shared default. | Fall back to the same global `default` ID for all omitted IDs. |
| **C3 · Stable ordering and pagination** | Force equal server timestamps and misleading device times; both devices and paginated reads return the same strict sequence, with no skipped/duplicate rows and user before assistant. | Sort or page by timestamp alone instead of the server sequence. |
| **C4 · Concurrent writes** | Use independent clients/DB connections and barriers for concurrent A/B writes to one conversation (including reversed model completion); every acknowledged turn appears exactly once, intact, with unique sequence IDs, correct attribution and identical order on both readers. | Allocate the next sequence outside the write transaction. |
| **C5 · Whole-turn atomicity** | Fail the second row insert and then read from another connection: no partial user/assistant pair and no success; a later healthy write works. | Commit the user row separately before writing the assistant row. |
| **C6 · Restart durability** | After a successful `/chat`, hard-stop process A and start process B on the same DB; both devices see identical message IDs, order and contents, and the next model call receives durable context; write enough turns to exceed the old ten-message RAM window. | Stop writing the completed turn to SQLite and retain it only in process memory. |
| **C7 · Safe retry if clients auto-retry** | Re-send an acknowledged request with the same client request ID after losing the response; return the existing turn without a second model call or append; a mismatched payload is rejected. | Ignore the existing request ID when dispatching a retried write. |
| **L1 · Message length and request size** | Whitespace-only input fails; exactly the configured character and encoded-size bounds pass in their respective fixtures; one unit over (including multi-byte Unicode) fails before any model/tool call or DB append. | Drop the encoded-size guard (also test a separate mutant dropping the character guard). |
| **L2 · Device message rate** | At the documented limit, the next request gets 429 with appropriate retry information before model or DB work; A cannot reset it by changing conversations, B's independent budget stays usable, and A recovers at the boundary. | Add conversation ID to the device rate-limit bucket key. |
| **L3 · Concurrent rate admission** | Fill all but one slot, release simultaneous A requests on separate clients/connections and admit exactly one; every rejected request produces no side effect. | Split the last-slot check and reservation into separate non-atomic operations. |

**How to run the gate:** Require the 128 baseline checks (adjust old unauthenticated fixtures to use authorized devices rather than weakening their behavior assertions) plus every applicable row above to pass with **zero skipped security/conversation checks**. Use real FastAPI dependencies and file-backed SQLite; fake only downstream providers/tools and clocks. Use barriers or instrumented repository hooks for races, not sleep-and-hope. Include a fresh OS process for restart; reopening a client in the same process can accidentally validate a cache. Inspect persisted rows and downstream call counters on both negative and positive cases. Run concurrency cases repeatedly after proving the hand-picked interleavings. If the release is single-process, state that explicitly; otherwise run cross-instance revocation, ordering and rate-limit cases in the deployed topology. For each applicable mutant, keep its failing test ID and the restored green run in the release checklist.
